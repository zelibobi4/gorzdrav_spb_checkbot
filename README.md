# Gorzdrav SPB Checkbot — расширенный форк

Telegram-бот для мониторинга свободных талонов на [gorzdrav.spb.ru](https://gorzdrav.spb.ru/) с уведомлениями в Telegram.

Это расширенный форк проекта [cucumberian/gorzdrav_spb_checkbot](https://github.com/cucumberian/gorzdrav_spb_checkbot). В этой версии основной упор сделан на более точный поиск подходящего времени и мониторинг сразу всех врачей выбранной специальности.

## Возможности

- **Фильтр по времени приёма**
  - `/evening` — искать талоны с 17:00 до конца дня;
  - `/time 18:00-23:00` — произвольный диапазон;
  - `/time_off` — убрать ограничение по времени.
- **Режим «любой врач этой специальности»**
  - выбирается после поликлиники и специальности;
  - бот проверяет реальный список `appointments` каждого врача;
  - удобно для стоматологов и других специальностей с большим количеством врачей;
  - служебного **«Дежурного врача»** можно исключить командой `/duty_off` и вернуть командой `/duty_on`.
- **Совместная фильтрация по дате и времени** — например, ближайшие 15 дней и только 18:00–23:00.
- **Ручная проверка `/check`** по текущим фильтрам, в том числе при выключенном мониторинге, с частичными результатами и диагностикой ошибок API.
- **Общий SQLite-кэш** фоновой и ручной проверки с TTL 60 секунд по умолчанию: повторный `/check` может ответить без нового обхода API.
- **Автоматическая миграция существующей SQLite-базы** без удаления старых пользователей и настроек.
- **Уведомление содержит конкретного врача, дату, время, кабинет и ссылку на запись**.
- **Мониторинг не отключается после первого найденного талона**: бот продолжает следить дальше.
- **Антиспам по снимку текущих талонов**: повторно тот же набор не отправляется; новое сообщение приходит только при появлении нового подходящего талона.
- В новом сообщении показывается актуальный список доступных талонов; уже исчезнувшие записи из него удаляются.
- Снимок хранится в SQLite и переживает перезапуск контейнера/VPS.
- Если подходящих талонов нет, мониторинг остаётся включённым и продолжает ждать.
- Ошибка API у одного врача не останавливает проверку остальных врачей и не считается исчезновением его талонов.

> Важная особенность API Горздрава: `freeParticipantCount` не всегда совпадает с фактически доступными `appointments`. Поэтому при активных фильтрах и в режиме «любой врач» бот проверяет реальные записи, а не только общий счётчик.

## Как работает мониторинг

1. Пользователь выбирает район → поликлинику → специальность.
2. Можно выбрать конкретного врача или **«👥 Любой врач этой специальности»**.
3. При необходимости задаётся горизонт поиска: например `/15`.
4. При необходимости задаётся время: например `/time 18:00-23:00`.
5. Команда `/on` включает мониторинг.
6. Пока подходящих записей нет, бот молчит и продолжает проверять.
7. При первом подходящем результате бот отправляет актуальный список талонов и **продолжает мониторинг**.
8. Если набор не изменился, новых сообщений нет. Когда появляется новый талон, бот снова присылает весь актуальный список подходящих талонов.
9. Если прежний талон исчез, он удаляется из внутреннего снимка и больше не показывается в следующих уведомлениях.

## Ручная проверка и кэш

Для `/check` нужны созданный профиль (`/start`) и выбранный врач или специальность (`/set_doctor`). Команда работает при включённом и выключенном мониторинге, учитывает ограничение по дням, диапазон времени и исключение дежурного врача в режиме «любой врач».

Ответ показывает до **10 ближайших подходящих талонов**, общее число найденных записей, число успешно проверенных врачей, ошибки API и количество исключённых дежурных врачей. Если часть врачей не ответила, результат явно отмечается как частичный: отсутствие талонов среди успешно проверенных врачей не означает, что их нет у остальных.

Кэш хранится в SQLite в таблице `user_check_cache` и доступен обоим процессам приложения:

1. Фоновая проверка сохраняет результат пользователя.
2. `/check` использует сохранённый результат, если он не старше `CHECK_CACHE_TTL_SECS` (по умолчанию **60 секунд**) и настройки поиска совпадают.
3. Если кэш отсутствует, устарел или настройки изменились, команда обращается к API и тоже сохраняет результат. Повторный `/check` в пределах TTL может использовать его.
4. В ответе указаны источник данных и возраст кэша. Свежий кэш может содержать частичный результат с ошибками API.

Изменение цели поиска, лимита дней, времени или применимого фильтра дежурного врача делает прежний кэш неподходящим. Переключение `/on` / `/off` не мешает использовать свежий кэш; статус мониторинга в ответе берётся текущий.

`/check` **не меняет состояние мониторинга и антиспам-снимок**, поэтому ручной запрос не подавляет будущие автоматические уведомления. Ошибка чтения или записи кэша не должна останавливать проверку: это оптимизация, а не обязательное условие работы.

## Антиспам и исключение дежурного врача

- Слот идентифицируется по врачу и времени приёма, а не только по внутреннему ID Горздрава.
- Неизменный набор талонов не создаёт повторных уведомлений. При появлении нового подходящего талона бот присылает актуальный список.
- Само исчезновение талона не создаёт сообщения. Если подтверждённо исчезнувший слот появится снова, он будет считаться новым.
- При ошибке API врача его прежние ключи временно сохраняются в антиспам-снимке, но неподтверждённые талоны не включаются в новое уведомление.
- Антиспам-снимок хранится отдельно от кэша, в `user_seen_appointments`, и переживает перезапуск при сохранении файла БД.

В режиме «любой врач» команда `/duty_off` исключает записи, имя которых начинается с «Дежурный врач» без учёта регистра, включая имена с пояснением в скобках. `/duty_on` возвращает их в поиск. По умолчанию дежурный врач **учитывается**.

Настройка индивидуальна для пользователя, сохраняется в SQLite и отображается в `/status`. При её изменении антиспам-снимок очищается, поскольку меняется набор отслеживаемых талонов. Для выбранного конкретного врача этот фильтр не применяется.

## Команды

| Команда | Описание |
|---|---|
| `/check` | показать свободные талоны сейчас; использует свежий кэш до 60 сек., иначе обращается к API |
| `/set_doctor` | выбрать район, поликлинику, специальность и врача либо режим «любой врач» |
| `/status` | показать текущую цель мониторинга и фильтры |
| `/on` | включить мониторинг |
| `/off` | отключить мониторинг |
| `/0` | снять ограничение по количеству дней |
| `/N` | искать в пределах N дней, например `/15` |
| `/evening` | искать только с 17:00 до конца дня |
| `/time 18:00-23:00` | задать произвольный диапазон времени |
| `/time_off` | отключить фильтр времени |
| `/duty_off` | исключить «Дежурного врача» из режима «любой врач» |
| `/duty_on` | снова учитывать «Дежурного врача» |
| `/help` | показать помощь |
| `/start` | создать профиль пользователя |
| `/delete` | удалить профиль пользователя |

## Быстрый запуск через Docker Compose

### 1. Клонирование

```bash
git clone https://github.com/zelibobi4/gorzdrav_spb_checkbot.git
cd gorzdrav_spb_checkbot
```

### 2. Настройка окружения

Создайте `.env` в корне проекта:

```env
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
CHECKER_TIMEOUT_SECS=60
CHECK_CACHE_TTL_SECS=60
```

`CHECKER_TIMEOUT_SECS` задаёт паузу между фоновыми циклами (если переменная не задана, в коде используется 120 секунд). Это не TTL кэша: `CHECK_CACHE_TTL_SECS` отдельно задаёт срок переиспользования результата. Длительность самого обхода API добавляется к паузе.

Стандартный `docker-compose.yml` хранит SQLite в `./data/`, поэтому база переживает пересоздание контейнера.

### 3. Запуск

```bash
docker compose up -d --build
```

Логи:

```bash
docker compose logs -f
```

Остановка:

```bash
docker compose down
```

## Запуск без Docker

Требуется Python 3.12.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r src/requirements.txt
```

Создайте `.env`:

```env
BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
DB_FILE=sqlite.db
CHECKER_TIMEOUT_SECS=60
CHECK_CACHE_TTL_SECS=60
```

Запуск:

```bash
python src/app.py
```

После запуска в Telegram выполните `/start` → `/set_doctor`, задайте нужные фильтры и проверьте результат через `/check`. Для постоянных уведомлений включите `/on`; настройки видны в `/status`. Повторный `/start` пересоздаёт профиль, поэтому не используйте его для обычной проверки существующих настроек.

## База данных

Используется SQLite.

Для пользователя сохраняются, в частности:

- Telegram ID;
- включён ли мониторинг;
- выбранный конкретный врач либо режим специальности;
- поликлиника и специальность;
- ограничение по дням;
- диапазон времени;
- учитывать или исключать служебного «Дежурного врача»;
- время последней активности.

При обновлении старой базы необходимые поля добавляются автоматически.

После установки зависимостей из `src/requirements.txt` запустите из корня репозитория:

```bash

python -m pytest -q
```

Для прицельной проверки антиспам-состояния, ручных результатов и кэша (из `src/`):


Тесты покрывают в том числе:

- миграцию старой SQLite-базы;
- фильтрацию по времени;
- режим «любой врач специальности»;
- возврат от режима специальности к конкретному врачу;
- сохранение настройки исключения дежурного врача;
- сохранение и сброс антиспам-снимка;
- форматирование ручной проверки и частичных результатов при ошибках API;
- сериализацию кэша, истечение TTL и отклонение результата при изменении фильтров;

## API

Проект использует публично доступные HTTP-эндпоинты Горздрава Санкт-Петербурга.

Полезная сторонняя документация API:
[egorantonov/gorzdrav wiki](https://github.com/egorantonov/gorzdrav/wiki/SPB-Gorzdrav-API-Documentation)

Примеры:

```text
/_api/api/v2/shared/districts
/_api/api/v2/shared/district/{districtId}/lpus
/_api/api/v2/schedule/lpu/{lpuId}/specialties
/_api/api/v2/schedule/lpu/{lpuId}/speciality/{specialtyId}/doctors
/_api/api/v2/schedule/lpu/{lpuId}/doctor/{doctorId}/appointments
```

## Производительность режима «любой врач»

В этом режиме бот запрашивает реальные `appointments` для каждого врача выбранной специальности. Если врачей много, один цикл проверки занимает заметно больше времени, чем мониторинг одного врача.

Это сознательный компромисс в пользу точности: счётчики API Горздрава могут показывать 0 свободных мест даже тогда, когда endpoint `appointments` возвращает доступные записи.
